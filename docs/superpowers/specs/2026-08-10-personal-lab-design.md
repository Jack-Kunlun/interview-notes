# 个人主页与技术产品实验室设计

## 背景

现有 `interview-notes` 是基于 VitePress 的独立前端面试知识库。它的内容边界和使用场景已经明确，应继续保留为独立仓库和独立应用，而不是迁入新的个人站点。

新项目使用 Nuxt Content 从零构建，定位不是另一套博客主题，也不是未经验证的商业平台，而是个人主页与技术产品实验室。它通过真实作品、开发记录和用户反馈逐步积累可信度，商业化只作为后续可能性，不在首版承诺职业辅导、AI 专家服务或付费会员。

## 产品定位

站点对外表达为：

> 一个前端开发者的个人主页与产品实验室，分享技术实践，开发对工作和生活有用的小工具。

站点承担四项职责：

1. 说明作者是谁以及正在做什么；
2. 展示已经完成或正在验证的真实作品；
3. 沉淀技术实践、产品开发记录和复盘；
4. 为潜在合作保留克制、清晰的联系入口。

“AI 职业成长”“前端求职内容”和“技术服务”是潜在演进方向，而不是首版同时铺开的业务栏目。后续方向以真实使用反馈决定。

## 成功标准

首版完成后应满足：

- 访客可以在首页快速理解作者、当前构建内容和已有作品；
- `interview-notes` 以正式作品呈现，主入口指向实际知识库应用；
- 至少有一个真实可用的站内工具，而不是演示占位页；
- 文章、作品和固定页面都能通过 Markdown 持续维护；
- 单个工具失败不会拖垮站点其他区域；
- 整个 Turborepo 可以通过一条 Docker Compose 命令构建并运行；
- 项目能够在不改变核心代码的前提下部署到任意支持 Docker 的轻量服务器。

## 非目标

首版不包含：

- 登录、会员、支付和管理后台；
- 评论、社交关系和云端收藏；
- 通用 AI 聊天或模型聚合；
- 运行时微前端和 Module Federation；
- 多个独立部署的工具应用；
- 域名迁移、ICP 备案和具体云厂商配置；
- 将 `interview-notes` 内容复制或同步到新仓库。

## 信息架构

主导航只保留四项：

```text
首页
作品
文章
关于
```

### 首页

首页回答五个问题：作者是谁、正在做什么、做过什么、最近在思考什么、如何联系。

首页采用控制台仪表盘结构，包含：

- 简短个人介绍和主要行动入口；
- 当前构建状态；
- 项目与文章数量等由内容集合生成的统计；
- 精选作品；
- 最近文章；
- 简短合作入口。

### 作品

“项目”“工具”和“实验”共用一个作品集合，通过类型与状态区分，不建立空的独立栏目。

作品类型：

- `project`：已经形成完整结果的项目；
- `tool`：可直接使用的工具；
- `experiment`：正在验证或可能停止维护的实验。

作品状态：

- `building`：开发中；
- `available`：可体验；
- `maintained`：持续维护；
- `archived`：已归档。

### 文章

首版使用标签而不是复杂分类。文章可以覆盖技术实践、产品开发记录、思考和复盘。文章数量形成规模后再决定是否增加专题页。

### 关于

关于页包含简短经历、技术方向、社交链接、联系方式和可接受的合作类型。“合作”不作为独立导航栏目。

## 仓库与系统架构

新项目采用 pnpm workspace 与 Turborepo：

```text
personal-lab/
├─ apps/
│  └─ web/                    # Nuxt Content 主站
│     ├─ app/
│     ├─ content/
│     └─ server/
├─ packages/
│  ├─ ui/                     # 设计令牌和公共组件
│  ├─ tool-kit/               # 工具协议与统一容器
│  ├─ shared/                 # 通用类型和无框架逻辑
│  └─ tools/
│     └─ jd-skill-radar/      # 首个真实工具
├─ package.json
├─ pnpm-workspace.yaml
└─ turbo.json
```

### `apps/web`

主站负责：

- 首页、作品、文章和关于页面；
- Nuxt Content 内容集合、查询和渲染；
- 工具路由与统一页面外壳；
- 导航、SEO、错误页和整体布局；
- 必要的 Nitro 服务端接口。

### `packages/ui`

提供设计令牌、基础控件、状态标签、卡片、表单元素和控制台风格组件。工具不得各自建立不兼容的基础视觉体系。

### `packages/tool-kit`

定义工具清单、异步加载协议、运行环境、加载状态、错误边界和反馈入口。主站只依赖该协议，不读取工具内部实现。

### `packages/shared`

只放不依赖 Nuxt 或浏览器界面的通用类型和纯函数。业务特定逻辑留在对应工具包内。

### 工具成长路径

所有工具先作为 workspace package 随主站构建和部署。只有在需要独立账号、数据库、技术栈或发布周期后，才迁移为 `apps/<tool-name>` 独立应用。首版不引入运行时微前端。

## 内容模型与数据流

Nuxt Content 管理以下集合：

```text
apps/web/content/
├─ articles/
├─ works/
└─ pages/
```

作品元数据至少包含：

- 标题、摘要、类型和状态；
- 发布时间与更新时间；
- 是否首页推荐；
- 实际应用地址 `appUrl`；
- 可选源码地址 `sourceUrl`；
- 可选复盘文章地址 `caseStudyUrl`；
- 站内工具使用的可选 `toolId`。

链接优先级固定为：

1. 外部作品的主要操作打开实际应用地址；
2. 站内工具的主要操作进入工具界面；
3. 源码地址只在开源时作为次级操作显示；
4. 未发布作品不显示虚假的体验按钮。

`interview-notes` 在新仓库中只有一个作品介绍文件。它的主要操作打开实际知识库应用，GitHub 源码仅作为可选次级入口。

### 工具注册

每个工具导出统一清单：

- 工具 ID 和显示名称；
- 异步组件入口；
- 运行环境；
- 功能状态；
- 所需浏览器或服务端能力。

作品 Markdown 使用 `toolId` 连接工具注册表。构建时校验所有 `toolId`，不存在或重复时构建失败。

首页的作品数、文章数、当前构建和精选内容从内容集合生成，不维护重复的手工统计。

## 视觉与交互方向

视觉采用已确认的 B1“控制台仪表盘”方向：

- 深色石墨背景与低对比网格；
- 高亮绿色作为主要交互和在线状态色；
- 紫色作为少量实验与次级状态色；
- 等宽字体承担状态、标签和技术标识；
- 中文正文使用可读性更好的系统无衬线字体；
- 卡片、边框、状态和统计形成实验控制台气质。

高密度控制台视觉主要用于首页、作品索引和工具工作台。文章详情与长文说明沿用相同设计令牌，但降低网格、卡片和状态信息密度，保证阅读体验。

所有交互必须支持键盘操作、清晰焦点、合理对比度和 `prefers-reduced-motion`。视觉状态不能只依赖颜色表达。

## 首个工具：前端岗位 JD 技能雷达

### 目的

帮助用户把一段前端招聘 JD 整理成可核对的技能信号和准备清单。工具只做文本信息整理，不判断岗位好坏、不评估用户能力，也不预测面试结果。

### 输入

首版只接受粘贴的纯文本 JD，不支持简历、PDF、Word、图片或多份 JD。

### 输出

分析结果包含：

1. 岗位概览：岗位名称线索、工作年限、学历、城市或工作方式、主要框架；
2. 技能分布：语言、框架、CSS、工程化、性能、Node.js、跨端、DevOps 与协作等维度；
3. 关键词明细：标准技能名、出现次数、上下文片段和“必须/熟悉/加分”等语气；
4. 准备清单：根据技能信号生成可勾选事项，并在存在对应内容时链接到 `interview-notes` 实际章节；
5. 导出：复制 Markdown、下载 Markdown 和清空重置。

### 分析流程

```text
JD 文本
  ↓
文本标准化与分句
  ↓
技能别名和关键词匹配
  ↓
上下文与语气规则
  ↓
分类、去重和权重归一化
  ↓
岗位概览、技能分布与准备清单
```

技能字典与界面分离，包含标准名称、常见别名、所属分类、基础权重和可选知识库地址。技能分值只表达当前 JD 中的文本强调程度。

### 页面状态

工具使用自适应双状态布局：

- 未分析时，输入区居中并占据主要空间；
- 分析完成后，切换为左侧输入、右侧结果；
- 用户修改已分析文本后，保留旧结果并提示内容已变化；
- 移动端始终使用输入在上、结果在下的单列布局；
- 长篇使用说明位于工作台下方，不挤入操作区域。

### 隐私

首版分析完全在浏览器执行：

- JD 文本不上传服务器；
- 不记录输入正文；
- 默认不跨会话保存；
- 导出文件只在本地生成。

后续如果加入 AI 服务，必须在发送前明确提示数据去向，并重新设计日志、保留期限和隐私说明。

## 错误处理

所有工具运行在统一 `ToolShell` 内，提供加载、错误、重试和反馈状态。工具异常只替换工具区域，不影响作品介绍、导航和其他页面。

JD 技能雷达处理以下边界：

- 空白或过短输入不给出误导性结果；
- 超长输入在分析前提示限制；
- 未识别到技能时展示可理解的空结果和改进建议；
- 无法解析的字段保持“未识别”，不凭空补全；
- 用户修改输入后明确标记结果已过期；
- 普通界面不暴露堆栈和内部错误对象。

## Docker 部署

首版使用一个 Nuxt/Nitro Node Server 容器。仓库提供：

- 多阶段 `Dockerfile`；
- `compose.yaml`；
- `.dockerignore`；
- `.env.example`；
- `/api/health` 健康检查。

标准部署命令：

```bash
docker compose up -d --build
```

镜像构建要求：

- 使用 Turborepo 裁剪 `apps/web` 所需依赖；
- 构建阶段与运行阶段分离；
- 运行镜像只包含 Nuxt `.output` 及必要运行文件；
- 使用非 root 用户；
- 密钥只通过运行时环境变量注入；
- 日志写入标准输出；
- 容器不依赖不可恢复的本地临时数据。

域名、TLS、反向代理和 ICP 备案由未来服务器环境处理，不放入首版应用容器。未来独立工具通过在 Compose 中增加服务扩展。

## 版本策略

实施当天从官方发布渠道核验依赖版本：

- Nuxt、Nuxt Content、Turborepo、pnpm、Vitest 等使用最新正式稳定版；
- 不使用 beta、RC、nightly 或 canary；
- Node.js 使用最新 LTS，不使用仅处于 Current 阶段的版本；
- 直接依赖锁定精确版本并提交 `pnpm-lock.yaml`；
- CI、本地和 Docker 使用相同 Node 主版本；
- Docker 使用明确标签的 Debian slim Node LTS 镜像，避免 Alpine 原生依赖兼容风险；
- 自动依赖工具只创建升级 PR，不自动合并。

“最新稳定版”以实施时兼容性验证通过的版本为准，而不是在生产构建中使用不受控的 `latest` 标签。

## 测试与验证

### 自动化测试

- `packages/shared` 与 JD 分析算法：单元测试；
- 技能别名、语气、分类、去重和权重：表格驱动测试；
- JD 工具组件：输入状态、结果状态、过期状态和错误状态测试；
- 工具注册表：重复 ID、缺失工具和无效元数据测试；
- Nuxt Content：集合 schema 与必填字段校验；
- 主站：页面集成测试；
- 核心访问路径：少量端到端测试；
- 仓库级：lint、类型检查和生产构建。

### 必测路径

- 首页统计和精选内容来自真实集合；
- 无效文章或作品路由返回正确 404；
- `interview-notes` 主按钮打开实际应用；
- 内部工具根据 `toolId` 正确加载；
- 单个工具异常不会导致整页崩溃；
- 空白、过短、典型和超长 JD 得到预期状态；
- Markdown 导出内容与界面结果一致；
- `docker compose up -d --build` 后健康检查通过；
- 桌面和移动端不存在关键操作遮挡或横向溢出。

## 后续演进原则

新功能只有在真实反馈支持时进入产品：

- 多 JD 对比、简历匹配和 AI 分析不在首版提前实现；
- 某个工具只有出现独立发布或运行需求后才升级为 `apps/*`；
- 付费、账号和数据库必须以已经验证的使用场景为前提；
- 新工具应继续遵守统一注册、错误隔离和隐私边界。
